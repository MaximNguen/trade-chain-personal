# Back2 — архитектура, авторизация и базовые API-слои

**Участник:** Нгуен Туан Минь  
**Роль:** архитектура, backend и тестирование

## Что я защищаю

Моя часть проекта — архитектурный каркас приложения. Я показываю, как запрос проходит от HTTP-роутера через сервисный слой в репозиторий, как устроена авторизация и почему frontend может работать с единым предсказуемым API.

## Что сделано

- Спроектирована начальная архитектура backend с разделением на доменные модели, HTTP-обработчики, сервисы и репозитории.
- Подготовлена ER-модель и базовая схема PostgreSQL для пользователей, товаров, категорий, цепочек и отзывов.
- Реализованы регистрация и вход пользователя.
- Настроена JWT-авторизация и middleware для защищённых маршрутов.
- Реализован API пользователей и получение текущего авторизованного пользователя.
- Подготовлены базовые DTO и интерфейсы сервисов и репозиториев.
- Выполнена часть работы над созданием объявлений и загрузкой изображений.
- Подключён Swagger и подготовлена документация API.
- Описаны пользовательские процессы в BPMN, проведено регрессионное тестирование и заведены баг-репорты.

Часть исходного каркаса позже дорабатывалась всей командой. На защите эта зона описывается как вклад в архитектурную основу проекта, а финальная механика обменов относится к `back3`.

## Как устроена архитектура

```text
Frontend
   ↓ HTTP / JSON
Router и middleware
   ↓
HTTP handler
   ↓
Service — проверки и бизнес-операции
   ↓
Repository — запросы к PostgreSQL
```

Такое разделение позволяет независимо изменять интерфейс, HTTP-контракт и хранение данных. Новая визуализация главной страницы не требует переноса бизнес-логики во frontend: он продолжает обращаться к тем же API.

## Что показать на финальной презентации

- Выбор подготовленного аккаунта и получение JWT без ручной работы с API.
- Защищённый переход: каталог доступен всем, а создание товара и обмен требуют входа.
- Возврат пользователя на исходный товар после авторизации.
- Создание объявления с изображением и получение его через API.
- Swagger с основными группами маршрутов.
- Общую схему прохождения запроса через слои приложения.

## Что должно быть проверено перед защитой

- Все пять демонстрационных аккаунтов входят с подготовленными данными.
- Пустой аккаунт корректно проходит сценарий создания первого товара.
- Защищённые маршруты не открываются без JWT.
- После входа frontend получает профиль через `/auth/me` и возвращается в исходный сценарий.
- Swagger соответствует реально подключённым маршрутам.
- Изображения товаров доступны после запуска Docker Compose.
